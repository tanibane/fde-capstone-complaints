Business Context
⏱ ~1 min
SAY
"Hi — in this demo I'm going to walk you through my capstone project: an Agentic Complaints Management System built for Clearview Retail Bank.

Clearview is a UK-regulated retail bank — 3.2 million customers, 420 branches, regulated by the FCA and PRA. They process over 50,000 complaints a month, entirely manually. That results in a 7 to 10 day average resolution time, a 40% mis-routing rate at triage, and analysts spending 60% of their time just gathering evidence from 4 disconnected systems. The bank is facing £12 million in FCA fines in 2026 from DISP deadline breaches alone.

My solution is a 4-agent agentic pipeline — Triage, Evidence, Policy, and Draft — that processes a complaint end-to-end in under 2 minutes, with full FCA compliance guardrails and a human-in-the-loop monitoring workbench. I used IBM Bob as my agentic IDE, and followed a specification-first approach throughout."

Process Studio — As-Is & To-Be
⏱ ~2 min
SHOW ON SCREEN
Open process-studio/as-is-process.md. Scroll through the 7 steps. Highlight the timing table and bottleneck annotations.
SAY
"The as-is process has 7 manual steps. The biggest bottleneck is evidence gathering — step 3 — which takes an average of 2.5 hours and accounts for 60% of analyst time. Analysts log into T24, CAMS, Salesforce, and Verint separately, export data manually, and piece it together.

There's also a critical compliance risk: 60% of vulnerable customers are not flagged at intake. And the 40% mis-routing rate means 2 in every 5 complaints start in the wrong team."
SHOW ON SCREEN
Open process-studio/to-be-process.md. Scroll through the 4 agent stages, showing the handshake payload blocks. Highlight the STP vs HITL decision matrix and escalation rules table.
SAY
"The to-be process replaces all 7 steps with a 4-agent pipeline that runs in under 2 minutes. Each agent passes a structured JSON handshake to the next — you can see the exact payload shapes here.

The key governance rules are enforced as hard-stops: any vulnerable customer blocks auto-dispatch. Redress over £150 is mandatory HITL. Legal threats stop the pipeline immediately and route to Investigations. And STP — straight-through processing — only fires when confidence is 90% or above and no guardrails are triggered.

Target impact: 30 to 50% cycle-time reduction, 2x cost savings, and 100% FCA DISP compliance."

SDD Contracts & IBM Bob
⏱ ~3 min
SHOW ON SCREEN
Open specs/COMPLAINTS-01/spec.md. Scroll through user stories US-03 (vulnerability guardrail) and US-04 (redress HITL rule). Show the acceptance criteria.
SAY
"I followed specification-first development — no code was generated until the contracts were complete and reviewed. The spec file defines 7 user stories, each with precise acceptance criteria. For example, US-03 specifies that vulnerability_flag equals true must force P1 priority and hitl_required equals true — and this must be enforced server-side, independent of whatever the LLM returns."
SHOW ON SCREEN
Open agents/schemas/triage-agent.schema.json. Then open agents/prompts/triage-agent.prompt.md. Show the ROLE, BOUNDARY, GUARDRAILS sections.
SAY
"Each of the 4 agents has a JSON schema that defines its exact input and output contract, and a prompt contract with 6 sections: Role, Boundary, Task, Guardrails, Output Format, and worked Examples.

The Boundary section is particularly important — it explicitly lists what the agent is NOT allowed to do. The Triage Agent cannot calculate redress, cannot query transaction data, and cannot proceed if the complaint text is fewer than 10 characters. This prevents scope creep and keeps each agent focused."
SHOW ON SCREEN
Open agents/pipeline/orchestrator.py. Show the hard-stop logic at lines 78–85 (vulnerability flag) and 82–85 (legal threat escalation).
SAY
"And critically — all guardrails are enforced twice. Once in the LLM prompt contract, and again as server-side Python logic in the orchestrator. So even if the model returned the wrong answer, the system would still enforce the correct behaviour. That's what makes this production-grade."

Live Agent Pipeline — 5 Complaints
⏱ ~3 min
SHOW ON SCREEN
Go to http://localhost:3000/complaints. Show the table with 300 seeded complaints. Show the filter dropdowns working — try Priority=P1, then Vulnerable=true.
SAY
"The database has 300 synthetic complaints covering all 6 intent types and 5 channels, with the correct distribution — duplicate charges at 28%, ATM failures at 22%, and so on. Around 14% are flagged as vulnerable customers. I can filter by any combination of priority, status, channel, and vulnerability."
RUN THESE 5 COMPLAINTS IN ORDER:
① Standard duplicate charge
CUST-001mobileSTP eligible
"I was charged twice for Netflix on 3rd January — £12.99 twice on the same day. Please refund one of them."
② Unauthorised transaction
CUST-005emailP1 · HITL
"Someone made a £350 unauthorised transaction on my account on 5th January. I did not authorise this payment."
③ Vulnerable customer
CUST-004branchVULNERABLE
"My husband passed away last month. I am elderly and devastated. I have called three times and nobody will help me close his account."
④ Data privacy
CUST-025emailP3 · low redress
"My personal data was shared without my consent. I want to know what data you hold and who you shared it with."
⑤ Legal threat
CUST-019mobileESCALATED
"I will be contacting my solicitor and taking legal action if this mortgage dispute is not resolved by end of this week."
FOR EACH COMPLAINT
  • Go to /complaints → click Run Pipeline on the complaint
  • While it runs (~30–60 sec), narrate what each agent is doing
  • When done: status changes to hitl_review, dispatched, or escalated
  • Click Trace to show the agent timeline on /monitor
SAY WHILE PIPELINE RUNS
"The pipeline is running now. First the Triage Agent is classifying the intent type, assigning priority, and running the FCA 13-category vulnerability classifier. Then the Evidence Agent is querying the mock T24 and CAMS systems to pull the transaction log. The Policy Agent is matching the FCA DISP rules and calculating the redress recommendation. Finally the Draft Agent is generating the resolution letter and setting the STP eligibility flag."
SAY after complaint ③ (vulnerable)
"Notice this one went straight to hitl_review — not dispatched. That's because the Triage Agent detected bereavement as an FCA Consumer Duty vulnerability marker. Once that flag is set, every downstream agent propagates it unchanged, and the Draft Agent is hard-coded to block auto-dispatch. The reviewer will see a red banner when they open it."
SAY after complaint ⑤ (legal threat)
"This one shows something interesting — the status is escalated, not hitl_review. The Triage Agent detected the word 'solicitor' and set the legal_threat_flag. The orchestrator immediately stops the pipeline after triage and routes it to Investigations. Evidence, Policy and Draft agents never run."

Monitoring Workbench + HITL + Reflection
⏱ ~2 min
SHOW ON SCREEN
Go to http://localhost:3000/dashboard. Point out the 5 KPI cards and 4 charts.
SAY
"The dashboard gives supervisors a live view — active cases, in-flight pipeline, P1 breach risk, average redress payout, and STP rate. It auto-refreshes every 15 seconds. The charts break down complaints by intent type, status, channel, and average redress for upheld cases."
SHOW ON SCREEN — Agent Monitor
Click Trace on complaint ③ (vulnerable customer). Show the timeline. Expand the triage payload — show the vulnerability_markers array and hitl_required=true.
SAY
"The agent monitor gives a full step-by-step audit trail. I can expand any event to see the exact JSON payload — the FCA rule references, the confidence scores, the data sources cited, the reasoning summary. Every decision is traceable and immutable — the audit_log table has PostgreSQL rules that block any UPDATE or DELETE."
SHOW ON SCREEN — HITL Review
Click Review → on complaint ③ (vulnerable). Show:
  • The red vulnerable customer banner at the top
  • The AI recommendation panel — outcome, confidence %, FCA rule, reasoning
  • Override the redress amount (e.g. change to £150) and add a justification note
  • Edit one line in the letter editor
  • Click Approve & Dispatch → show success confirmation
SAY
"The HITL panel shows the analyst everything they need to make a decision — the AI's recommendation, the confidence score, the FCA rule it applied, and the full reasoning. The analyst can accept the AI's redress calculation or override it with a mandatory justification note. They can also edit the resolution letter inline before dispatch.

There are three decision pathways: Approve and Dispatch, Request Re-triage — which sends it back through the pipeline — or Escalate to Investigations for legal cases."
CLOSING REFLECTION
"If I were to do this again, I would spend more time integrating the real Context Studio hybrid queries at runtime — right now the ontology is exported and validated but the agents use embedded FCA rule logic rather than live graph queries. I'd also add WebSocket push updates to the dashboard rather than polling, and build out the notification service so letters are actually dispatched via email.

But the core architecture — specification-first, dual-layer guardrails, tamper-proof audit trail, and zero vulnerable-customer misses — is production-grade. Thank you."
